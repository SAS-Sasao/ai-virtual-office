name: project-eventlog-identity-dedup-log-layer
description: EventSource auto-reconnect re-sends restore events; dedup this at the app/lib log layer (EventLogBuffer), never inside game/OfficeState.applyEvent
metadata:
  type: project
---

**Bug**: `EventSource` auto-reconnects on any transient network blip, and `GET /api/stream` re-sends `event: restore` (latest-per-session replay from SQLite) on every fresh connection. `OfficeView.applyRawEvent` used to unconditionally `eventLogBuffer.push(parsed); setEventLog(...)` after every `state.applyEvent(parsed)` call — so each reconnect double-recorded the same events into the sidebar log and made `NarrationBar` (`buildNarrationText(eventLog[0])`) re-announce stale events (e.g. "退社しました" repeating on a harmless reconnect blip).

**Rejected fix** (Phase 1 design review caught this, composite 0.66 fail on first pass): gating on `OfficeState.applyEvent`'s return value. Doesn't work — `office-state.ts`'s ordering guard is `< 0` (strict), so **equal-seq resends from an active session are NOT rejected** (`applyEvent` returns `true`/applied for identical-seq resends by design — `office-state.test.ts` pins "same-seq resend is idempotently reapplied"). Restore replay of an *active* session has the exact same seq as what's already applied, so this gate never fires. Also, `session_end`'s delete+notify is a legitimate state transition, not a duplicate to suppress — conflating the two would break the "退社しました" narration for real departures.

**Actual fix**: dedup lives entirely in `apps/web/app/lib/event-log.ts`'s `EventLogBuffer`, never touching `apps/web/game/office-state.ts`. `push(event): boolean` now computes an identity key (`${sessionId}#${seq}` if `seq` present, else `${sessionId}#${ts}#${type}`) and keeps a `Map<sessionId, mostRecentIdentity>` (not a fixed-size ring — a ring risks eviction holes when many concurrent sessions are interleaved, since restore resends per-session need to be compared against *that session's* last-seen identity specifically, not some global recency window). If the incoming identity matches the session's last-recorded one, `push` no-ops and returns `false`; otherwise it records and returns `true`. `OfficeView.tsx`'s `applyRawEvent` gates `setEventLog(...)` on the boolean, but **still calls `state.applyEvent(parsed)` unconditionally** — `OfficeState`'s own idempotent-resend semantics are completely untouched.

**Why this is the right layer for `ui-dev`**: this kind of "SSE/EventSource reconnect produces duplicate application-layer effects" bug is generic to any React UI consuming a raw event stream, and the fix pattern (identity-keyed last-seen map per logical stream/session, applied at the UI/display layer) generalizes beyond this specific narration bug. When a similar "reconnect causes visible duplication" bug shows up elsewhere in the UI (e.g. a future toast/notification queue), reach for this same pattern before touching `game/` — `game/office-state.ts`'s ordering semantics are deliberately about physical/state consistency (idempotent resend = correct), not about "has the UI already shown this to the user", which is a different, UI-layer concern.

**Testing**: fully unit-testable against the exported `EventLogBuffer` class directly (`apps/web/app/lib/event-log.test.ts`) — no need to reach into `OfficeView`'s `useEffect` closure. Push the same event object (or a shallow copy) twice, assert second call returns `false` and `getItems()` is unchanged; also assert `buildNarrationText(getItems()[0])` doesn't change across the duplicate push (regression guard for the actual user-visible symptom, not just the data structure).
