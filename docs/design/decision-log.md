## ADR-001: コアアプリを Docker 管理しない

| 項目 | 内容 |
|---|---|
| 日付 | 2026-07-20 |
| ステータス | 採用（Accepted） |
| 決定 | **アプリ本体（Relay / Next.js / adapter）の開発・実行・配布に Docker を使わない。** ただし後述の 2 用途に限り、該当マイルストーンで限定的にコンテナを使う |

### 背景

M0 着手前の環境整備の過程で「このアプリケーションは Docker 管理したほうがよいのでは」という論点が挙がった（2026-07-20 相談）。

### 不採用の理由

1. **本アプリは「ホスト環境の観測者」であり、Docker は観測対象との間に隔離壁を作る。** 入力はすべてホスト側にある — Claude Code hooks は開発者マシンの `localhost:4100` へ curl し（要件 §5.2）、保険系はホストの `~/.claude/projects/**/*.jsonl` を読み、adapter は組織リポジトリ（`~/cc-sier-organization` 等）の masters / task-log を読む。コンテナ化するとこれら全てのボリュームマウントが必要になる上、FR-4 の帰属推定は hooks イベントの `cwd`（ホスト絶対パス）と登録リポジトリパスの照合で動くため、**コンテナ内外のパス差異が帰属ロジックを壊す**
2. **配布モデルが npx 前提（NFR-5）と衝突する。** 「`pnpm dev` + `npx ai-office-relay` の 2 プロセスで完結」が可搬性要件であり、想定ユーザー（Claude Code 利用者）は Node を必ず持つ。Docker Desktop の前提追加は導入障壁の純増で、`npx ai-office setup` の導入・撤去体験（要件 §5.1）と噛み合わない
3. **Docker の主メリット（環境固定）は既に別手段で担保済み。** corepack + `packageManager: pnpm@9.0.0` 固定 + lockfile + [dev-environment.md](../dev-environment.md)（AI 指示書による検証・構築の自動化）で解決している。また WSL2 + Docker はポートフォワーディングの層を増やし、NFR-2（hooks が Claude Code を一切ブロックしない）に対する障害点を追加する方向に働く
4. **本番デプロイ経路にもコンテナが登場しない。** M3 は Vercel（serverless）+ マネージド Postgres / Realtime（AR-3、アーキ設計 §3.3）であり、コンテナホスティングは使わない

### 限定的に採用する 2 用途（アプリ本体は含めない）

| 時期 | 用途 | 理由 |
|---|---|---|
| M2 | CI の視覚回帰テスト（`toHaveScreenshot`）を Playwright 公式 Docker イメージ内で実行 | フォント・レンダリング環境差によるフレークの根絶（設計書 §5.4 のフレーク対策と整合）。第 2 層（視覚回帰）に限定し、第 1 層（Debug State API の状態 assert）はコンテナ不要 |
| M3 | SQLite → Postgres 移行検証用の使い捨て Postgres を docker-compose で 1 サービスのみ起動 | Drizzle スキーマの互換検証用。アプリ本体はコンテナに入れない |

### 再検討の条件（このいずれかが起きたら本 ADR を見直す）

- 配布対象が「Node を持たないユーザー」へ拡大したとき
- デプロイ先が Vercel からコンテナホスティング（ECS / Cloud Run 等）へ変わったとき
- 観測方式が hooks / ローカルファイル読み取り以外（ネットワーク API 経由等）へ変わり、ホスト密着の必然性が消えたとき

## ADR-002: オフィス描画は「手続き描画を正、背景画像を任意の装飾レイヤー」とするハイブリッド構成

| 項目 | 内容 |
|---|---|
| 日付 | 2026-07-20 |
| ステータス | 採用（Accepted） |
| 決定 | **部屋・家具・キャラの配置と当たり判定は `OfficeLayout` からの手続き描画を正とする。** フロアごとの一枚絵背景（`backdrop`）は、その下に敷ける**任意の装飾レイヤー**として設計に加える。キャラクターは CSS ドット絵ではなく **PNG スプライトシート**で描画する |
| 起点 | フロントモック `AI Virtual Office.dc.html` の 2026-07-20 改訂（一枚絵背景 + PNG スプライトへ全面移行し、CSS による部屋・家具描画を `showCss:false` で無効化した） |

### 背景

モックの当該改訂は、オフィスの見た目を「手描きの一枚絵（`uploads/*.png`）を `background-size:cover` で敷き、その上に PNG スプライトのキャラを置く」方式へ切り替えた。ドット絵の密度と質感は CSS 手続き描画より明確に良い。一方でモックは部屋・家具の CSS 描画パスを丸ごと無効化しており、これをそのまま実装仕様に採ると要件と衝突する。

### 一枚絵に全面移行しない理由

| # | 理由 |
|---|---|
| 1 | **FR-3（マスタからの間取り生成）が成立しない。** 部署の増減・`standby` 化・ロール追加が起きても、固定 PNG は追従できない。CC-SIer マスタ駆動は本アプリの差別化要素そのもの（CLAUDE.md）であり、譲れない |
| 2 | **FR-6（エディタでの家具配置・`custom` フラグ保存）が成立しない。** 一枚絵の上では家具を動かせず、保存すべき配置データも存在しない |
| 3 | **当たり判定と経路探索の情報源が消える。** BFS はタイルグリッド上の通行可否を必要とし、これは画像からは復元できない |
| 4 | 組織が変わるたびに人手で背景を描き直す運用になり、**組織インポートの自動化という前提が崩れる** |

なおモック側も `rooms`（座標・サイズ・トリガー語）のデータ構造自体は保持しており、レイアウト情報を捨てたわけではない。捨てられたのは描画パスだけである。

### 採用する構成（レイヤー順）

| z | レイヤー | 生成元 | 必須 |
|---|---|---|---|
| 0 | `backdrop`（フロア一枚絵） | 手描き素材。`OfficeLayout.backdrop` で任意指定 | 任意 |
| 1 | 床・壁・部屋 | `OfficeLayout`（cc-sier-adapter がマスタから生成） | **必須** |
| 2 | 家具 | `OfficeLayout.furniture`（エディタで編集・`custom` フラグ） | **必須** |
| 3 | キャラクター | PNG スプライトシート + 状態機械 | **必須** |
| 4 | オーバーレイ（吹き出し・リンク線・ホバーカード・ホワイトボード拡大） | ランタイム状態 | **必須** |

- `backdrop` が指定された場合、レイヤー 1〜2 は**装飾を背景に委ねて簡略描画に落とせる**ようにする（部屋の枠線・名前プレートと当たり判定は残す）。ただし**レイヤー 1〜2 のデータは常に存在する**ことを不変条件とする
- `backdrop` の座標系は `OfficeLayout` のタイルグリッドに一致させる（`cover` によるスケール差を持ち込まない）。一致しない素材は採用しない
- `backdrop` 未指定でも**単体で成立する見た目**を維持する。これが崩れると事実上 1 の全面移行と同じになる

### 影響

- `packages/protocol` の `OfficeLayout` に任意フィールド `backdrop` を追加する（M1 以降。追加時は `/protocol-change` の手順に従う）
- `apps/web/game/renderer.ts` に backdrop レイヤーの描画順を追加。`apps/web/game/sprites/` は CSS ドット絵定義ではなく**スプライトシート（PNG + フレーム定義）**を前提にする
- 素材は NFR-6 に従い CC0 / CC-BY 系のみ。モックの `sprites/*.png` / `uploads/*.png` は**プレースホルダーであり実装には流用しない**

### 再検討の条件

- FR-3 / FR-6 が要件から外れたとき（マスタ駆動の間取り生成とエディタを両方やめる判断をしたとき）
- 手続き描画のままでモックと同等の見た目の質に到達できないことが、実装を試みた上で確認されたとき

## ADR-003: FR-4 帰属規則 2（ブランチ名）は dormant として実装する

| 項目 | 内容 |
|---|---|
| 日付 | 2026-07-25 |
| ステータス | 採用（Accepted） |
| 決定 | FR-4 の規則 2（ブランチ名 `{org}/...` プレフィックスからの組織帰属）は要件どおり実装するが、**現行運用では発火しない（dormant）**ことを明記した上で維持する。優先順位は「規則 1（cwd 前方一致）→ 規則 2（org 未確定時のみ）→ 規則 3（subagent_type）→ 規則 4（帰属なし）」 |

### 背景（実測）

cc-sier-organization は単一 `.git` の mono-repo に 3 組織 + 単一 `.active` を持ち、実ブランチは `main` / `docs/...` / `claude/...` で `{org}/...` 規約を使っていない（2026-07-25 実測）。よって cwd がリポジトリ内なら規則 1 が常に成立し、規則 2 の出番が無い。branchOrgs との前方一致は組織 ID に限られるため、実ブランチ名が誤マッチする偽陽性も生じない。

### 再評価のトリガー（いずれかが起きたら規則 1↔2 の優先順位を見直す）

- cc-sier 側が `{org}/...` のブランチ命名規約を採用したとき
- 組織リポジトリの登録が mono-repo 以外（組織ごとの独立リポジトリ）に拡張されたとき

## ADR-004: スプライトは自前生成シートで先行し、PNG ロードは差し替えで対応する

| 項目 | 内容 |
|---|---|
| 日付 | 2026-07-25 |
| ステータス | 採用（Accepted・人間承認済み） |
| 決定 | キャラクター描画は ADR-002 のとおり**スプライトシート方式**とするが、シートの供給源は当面 **UI モック由来のピクセルマップ（自作コード）から実行時に offscreen canvas へ生成**する。外部 PNG 素材の選定・同梱は行わない |
| 関係 | ADR-002 の「PNG スプライトシート」の**実装段階付け**（supersede ではない）。`SpriteSheet` インターフェースが接続点で、将来 `loadSpriteSheetFromImage(png)` を追加すればレンダラ側は無変更で PNG に差し替わる |

### 理由

1. 外部素材ゼロのため **NFR-6 のライセンス確認・出典表記が不要**（フッタ「素材未使用」を維持）
2. UI モック v2/v3 のドット絵と**同一の見た目**（同じピクセルマップを移植するため）
3. 素材選定は見た目の好みとライセンス検証が絡む人間の判断であり、M1 の受入基準（動作・状態遷移の可視化）をブロックしない

### 再評価のトリガー

- 本物のドット絵素材（歩行アニメの質・多様な見た目）が必要になったとき（M2 の視覚回帰導入前が望ましい）
- 公開デモ（M3）で見た目の完成度を上げるとき

## ADR-005: キャラスプライトにユーザー自作 PNG（オフィスシート）を採用する

| 項目 | 内容 |
|---|---|
| 日付 | 2026-08-01 |
| ステータス | 採用（Accepted・M2-1） |
| 決定 | キャラクター描画のシート供給源を、ADR-004 の自前生成シートから**ユーザー自作の PNG スプライトシート**（`apps/web/public/assets/characters/office.png`・1536×1024・オフィス系 8 体・4 列×2 行＝1 セル 384×512）へ差し替え本番化する。renderer は `SpriteSheet` 接続点に `loadSpriteSheetFromImage(image, cell)` を実装し、`cellFor(role, dept)` で 3 org・15 ロール・8 dept を 8 セルへ決定的にマッピングする（dept 起点・8 セル<15 ロールのため複数ロールが同一セルを共有＝制服的表現） |
| 関係 | ADR-004（自前生成先行・PNG は後日差し替え）の**予定どおりの差し替え本番化**（supersede ではなく段階の完了）。ADR-002 の PNG スプライトシート方針の具体化 |

### 実装上の割り切り

1. **単一正面ポーズ + bob**。素材は 1 ポーズのみで歩行フレームが無いため、`left` は水平反転（h-flip）、`up`/`right`/`down` は正面をそのまま描く（pose は無視。歩行時の脚アニメ・背面ドット絵は PNG では出ない＝モックと同じ静止スプライト表現）
2. **画像ローダは opt-in**（`RendererDeps.spriteImageLoader?`）。未注入時は `createGeneratedSpriteSheet` にフォールバック（＝既存 renderer テストは node 環境で `new Image()` を叩かず無回帰）。`new Image()`/DOM は OfficeView（React 側）に閉じ込め、`apps/web/game/` は React・DOM 非依存を維持する（NFR-7）
3. **初回ロードの一瞬の差し替え（generated→PNG）を許容**。シート画像のロード完了フレームで `spriteCache` を 1 回だけクリアして PNG に切り替える。ロード失敗（reject）は生成スプライト据え置きで再試行しない
4. **フォールバック（`createGeneratedSpriteSheet`）は残置**。未ロード・ロード失敗・ローダ未注入時の描画を保証する

### NFR-6（ライセンス）の解釈

- 出自は**ユーザー本人の申告**（2026-07-26 の会話で「アートは自作」と明示）。自作＝プロジェクトオリジナル素材のため、`requirements.md:150` / `CLAUDE.md` 開発規約 5 の「**ピクセル素材は CC0 / CC-BY 系のみ**」という文言が対象とする**外部配布素材の制約の対象外**である
- ただし**出典表記は自作でも必須**とする。クレジットは「作: プロジェクトオーナー（プロジェクトオリジナル）」として `README.md`（ライセンス表記節）と画面フッターの両方に記載する
- この解釈（外部素材＝CC0/CC-BY 限定 / 自作＝制約対象外だが出典必須）を正本レベルで明示する。requirements.md:150・CLAUDE.md 規約 5 の文面自体は据え置き、本 ADR がその適用範囲を補足する相互参照とする

### 再評価のトリガー

- ファンタジー系/混成シート・per-org テーマ・部屋 backdrop を導入するとき（`image/` に温存中の 4 枚）
- 歩行フレーム化・4 方向本格対応・オフライン画像パイプライン（sharp 導入）を行うとき
